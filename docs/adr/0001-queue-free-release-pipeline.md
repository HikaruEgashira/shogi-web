# ADR-0001: キューを持たないリリースパイプライン

## ステータス

採用（2026-10-15）

## コンテキスト

Anthropic の "Redesigning source control"（2026-10-13）は、エージェントが主体の開発ではマージキューの全域ロックが成立せず、post-merge / pre-deploy の自動検証と自動復旧で置き換えると述べる。本リポジトリの旧パイプラインは次の性質を持っていた。

- ワークフロー全体を1つの concurrency group で直列化していた。GitHub は同じ group の待機中 run を1つしか保持しないため、連続 push の中間コミットは run を取り消され、`releases/<commit>/` を持たなかった。
- 検証はヘッダー・チェックサム・ファイル存在の整合のみで、読み込み後に動かないページを検出できなかった。
- ロールバックは README の手順書で、S3 間コピーに `--metadata-directive REPLACE` を欠いていた。手順通りに実行するとエントリページが `immutable, max-age=31536000` のまま公開され、以後の配信がキャッシュに隠れる。
- PR 経由の取り込みは auto-merge が無効で、ruleset も無かった。

## 決定

- 直列化の範囲を公開エントリページの切り替えだけに縮める。全コミットが `releases/<commit>/` に並列で公開され、切り替えは `production` group で1本化し、より新しいコミットが既に公開中なら省略する。
- pre-deploy 検証に headless Chrome の実走（`scripts/play.mjs`）を加え、候補 URL・公開後・定期監視の3点で同じ検証を行う。DevTools Protocol を直接使い、依存を追加しない。
- 切り替え後の検証に失敗したら直前に公開していたリリースへ自動で戻し、ジョブを失敗させる。手動手順は `Roll back` ワークフローと `scripts/promote.sh` に置き換える。
- PR からの取り込みは ruleset（`build` 必須、削除・force push 禁止、管理者 bypass）と auto-merge で受け付ける。

## 理由

- 直列化が必要な資源はエントリページだけである。リリースディレクトリは不変パスなので並列公開で競合しない。
- 製品の検証はブラウザでしか成立しない。Playwright はこのリポジトリの依存ゼロ方針と合わず、必要な操作は CDP の5コマンドで足りる。
- 人が見ていない前提では、検知だけでなく復旧まで機械が行う必要がある。

## 結果

- push から本番反映までの時間は変わらない（約1〜2分）。並行 push が互いの run を取り消さなくなる。
- 受け入れるリスク: `production` group で待機中の切り替えは、より新しい run に取り消される。その run のビルドが失敗すると中間コミットは公開されないが、修正を前に進めることで回復する。
- 受け入れるリスク: `Watch production` は検知のみで、本番の遠隔測定は方針として存在しない。
